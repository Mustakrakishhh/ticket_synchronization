# Выкладка допуслуг в карточку билета

Изменения пока локальные. Публикация на GitHub и установка на Timeweb отдельно
не выполнялись. Изменение схемы MySQL, ключей API или cron не требуется.

## Файлы приложения

Сохраните резервную копию заменяемых файлов. Новые классы загрузите перед кодом,
который их использует. Замену выполняйте между запусками worker либо с временно
приостановленным расписанием синхронизации.

Новые файлы:

```text
src/Provider/Trivio/TrivioPricing.php
src/Sync/TicketAdditionalServices.php
src/Sync/AdditionalDocumentSync.php
src/Provider/TravelDocumentCollectionProviderInterface.php
```

Рабочий `.env`, содержимое `var/`, базу данных и токены заменять не нужно.
Зависимости не менялись; изменение `composer.json` добавляет только тест.
При включённом OPcache примените обычную для хостинга процедуру обновления кода.

## Настройка

1. Обновите приложение и на шаге 4 обновите список полей.
2. Сопоставьте «Виды доп. услуг» с полем **Строка, множественное**.
   Можно создать его кнопкой прямо в приложении. Это не поле «Список» с ID вариантов.
3. Для Trivio сопоставьте «Документы дополнительных услуг» с отдельным
   множественным полем **Файл**. Основной билет должен оставаться в другом поле.
4. Поле «Стоимость» уже получает итог билета с комиссией и связанными допуслугами.
   Дополнительно можно сопоставить цену без комиссии, комиссию и сумму допуслуг.
5. Включите загрузку документов и обновление существующих карточек.
6. Запустите ручную сверку за период нужного заказа. Проверьте сумму и файлы
   одного заказа в Trivio и Bitrix24; повторный запуск не должен создавать дубль.

Подтверждения `integrationFeedback` не отправляются. Вложения произвольных
услуг и автобусного багажа берутся из `service_files` через `getFileContent`
File API с существующей сессией Client API, даже если у услуги нет `ticketId`.
Документы допуслуг без вложений и собственного `ticketId` не подменяются документом основного билета; при
недоступности файла Trivio повторная проверка выполняется при следующем запуске.
