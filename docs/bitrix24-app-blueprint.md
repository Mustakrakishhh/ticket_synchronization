# Шаблон серверного приложения Bitrix24

Этот документ фиксирует повторно используемую структуру, чтобы для следующих
проектов не искать другой пример авторизации.

## Поток установки

1. Bitrix24 открывает `public/install.php`.
2. `InstallationRequest` принимает как плоские `AUTH_ID`, `REFRESH_ID`,
   `DOMAIN`, так и объект `auth`.
3. Если контекста недостаточно, страница вызывает `BX24.refreshAuth()`.
4. Backend проверяет `app.info`, сохраняет установку по `member_id` и вызывает
   регистрацию обработчиков приложения.
5. Браузер завершает установку через `BX24.installFinish()`.

## Многопортальная модель

- `member_id` - первичный ключ арендатора.
- Для тиражного приложения `BITRIX24_CLIENT_ID` и
  `BITRIX24_CLIENT_SECRET` общие и хранятся только в окружении сервера.
- OAuth-пара каждой установки хранится в `tenants.oauth_payload`,
  зашифрованной AES-256-GCM.
- Новая пара токенов после refresh атомарно заменяет старую пару того же
  `member_id`.
- Ключи Aviasales, Smartway и Trivio хранятся в
  `provider_connections.credentials_payload`, отдельно для каждого портала.
- Публичный каталог - только `public/`.

Локальное приложение подходит для разработки на одном портале. Одна
marketplace-регистрация предоставляет общие client id/secret для всех порталов,
поэтому тот же backend становится многопортальным без изменения модели данных.

## Защита интерфейса

- UI открывается из Bitrix24 и получает подписанную HttpOnly cookie.
- Cookie содержит `member_id`, срок действия и случайный CSRF-токен.
- Для iframe в HTTPS применяется `SameSite=None; Secure`.
- Все изменяющие запросы требуют `X-CSRF-Token`.
- API никогда не возвращает access token, refresh token или ключи провайдеров.
- `ONAPPUNINSTALL` после проверки `application_token` удаляет OAuth-токены,
  ключи провайдеров, настройки, курсоры и журнал арендатора.

## Контракт CRM

- `crm.type.list` - список смарт-процессов.
- `crm.item.fields` - доступные поля выбранного процесса.
- `crm.category.list` - воронки выбранного смарт-процесса.
- `crm.status.list` - стадии выбранной воронки.
- `crm.item.add` - создание карточки.
- `crm.item.update` - обновление покупки, обмена или возврата.

Обязательная дедупликация должна работать в двух местах:

1. уникальный ключ `(member_id, provider, entity_type_id, external_id)` в таблице
   `sync_items`;
2. обязательное пользовательское поле `external_id` в карточке Bitrix24 для
   диагностики и аварийного восстановления связей.

Перед записью тип услуги преобразуется в общий словарь, а затем направляется по
настройке `serviceRoutes` в нужные `categoryId` и `stageId`. Поэтому авиабилеты
и проживание могут находиться в разных воронках одного смарт-процесса.

## Что необходимо перед публикацией в Маркете

- развернуть управляемый MySQL и выполнить проверочный перенос SQLite;
- добавить ротацию ключа шифрования;
- проверить `ONAPPUPDATE`, `ONAPPUNINSTALL` и повторную установку на тестовых порталах;
- подготовить политику обработки персональных данных;
- добавить аудит действий администратора и срок хранения payload;
- провести нагрузочные тесты и тесты параллельного refresh token;
- определить тарифы и ограничения провайдеров для каждой компании.
