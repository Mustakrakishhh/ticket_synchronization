# Bitrix24 Travel Sync

Серверное приложение Bitrix24 для синхронизации билетов, проживания и связанных
затрат из Aviasales для бизнеса, Smartway и Trivio в смарт-процессы CRM.
Пользователь подключает провайдеров, выбирает смарт-процесс и воронки,
сопоставляет поля и задаёт расписание в интерфейсе приложения.

**Стек:** PHP 8.2+, B24PhpSDK, Symfony HttpClient, PDO, MySQL / SQLite,
JavaScript, HTML/CSS, OAuth 2.0, REST, JSON-RPC и SOAP.

## Возможности

- установку локального приложения Bitrix24 и серверное обновление OAuth-токенов;
- хранение нескольких порталов по `member_id`;
- AES-256-GCM шифрование OAuth-токенов и ключей провайдеров;
- мастер подключения провайдеров;
- выбор смарт-процесса через `crm.type.list`;
- живую загрузку его полей через `crm.item.fields`;
- серверный кэш справочников Bitrix24 с безопасным возвратом последней успешной копии;
- выбор воронки и начальной стадии для каждого типа услуги;
- настройку mapping и правил синхронизации;
- гибридный адаптер Trivio: чтение очереди Integration API (SOAP) без `integrationFeedback` и сверка Client API (JSON);
- единый формат для авиа, проживания, ж/д, трансферов и остальных услуг;
- идемпотентные `crm.item.add` / `crm.item.update`;
- ручной запуск, журнал, курсоры и блокировку параллельных запусков;
- внутреннюю OpenAPI-спецификацию;
- удаление токенов, ключей и данных арендатора при `ONAPPUNINSTALL`.

## Инженерные решения

Разные форматы провайдеров приводятся к единой модели `TravelItem`. Связь с
карточкой хранится по порталу, провайдеру, типу смарт-процесса и внешнему ID.
Контрольные суммы позволяют пропускать записи без изменений; после неоднозначного
таймаута создания приложение ищет карточку по внешнему ID, прежде чем повторять
создание. Очередь и блокировки защищают фоновые запуски от пересечения.

Интерфейс настройки отделён от фоновой обработки. Справочники Bitrix24
кэшируются, секреты шифруются, сессия интерфейса защищена подписью и CSRF.
Уведомления имеют отдельную очередь доставки, чтобы ошибка отправки не
обнуляла результат синхронизации.

Для Trivio реализованы объединение допуслуг с билетом, расчёт стоимости со
сборами и получение прикреплённых PDF, включая багаж автобуса. Несколько
документов записываются в множественное файловое поле. Названия допуслуг
передаются массивом в множественную строку.

## Статус и границы проекта

Проект используется как серверная интеграция с локальной установкой Bitrix24.
В коде предусмотрена изоляция данных нескольких порталов, но публикация и
модерация в Bitrix24 Маркете — отдельный этап, а не заявленная готовая возможность.
Полнота данных зависит от API и прав аккаунта конкретного провайдера; поддержка
сборов и вложений Trivio не означает идентичной поддержки у остальных сервисов.

В репозитории нет рабочих токенов, реквизитов компаний, базы с заказами,
пользовательских PDF и эксплуатационных логов. Для установки нужны собственные
реквизиты приложения Bitrix24 и аккаунты провайдеров.

очереди Trivio. Интеграционные тесты синхронизации используют SQLite в памяти.
Полный набор — `composer check`; для теста YAML-контрактов дополнительно требуется
PHP-расширение `yaml`. Эти тесты не заменяют проверку на реальном портале и MySQL.

Описание OAuth: [базовый контракт](docs/bitrix24-oauth-base.openapi.yaml).
Другие материалы: [контракт приложения](docs/openapi.yaml),
[архитектура](docs/bitrix24-app-blueprint.md),
[MySQL](docs/mysql-migration.md), [подготовка к Маркету](docs/marketplace-readiness.md).

`bin/sync.php` ставит в очередь синхронизации, для которых наступил выбранный интервал,
а затем обрабатывает очередь вне браузерного HTTP-запроса. Ручная кнопка также только
создаёт задачу; поэтому cron должен запускаться каждую минуту. Перед первым production-запуском обязательно проверьте
подключения кнопкой в мастере и выполните ручную синхронизацию на тестовом портале.

## Trivio и параллельная интеграция с 1С

Приложение не отправляет `integrationFeedback` в Trivio: подтверждение операций
остаётся за интеграцией с 1С. Повторно полученные операции сопоставляются по
стабильному внешнему ID и сохранённым полям карточки; без изменений карточка
пропускается, при изменении обновляется. Ошибки и результаты сохраняются локально.

Для дополнительной сверки заказов укажите логин и пароль Client API: если 1С
подтвердит операцию раньше очередного запуска Bitrix24, заказ может быть получен
через `getOrders` / `getOrder` за выбранный период. Доступность всех финансовых
данных возвратов через Client API требует отдельной проверки у Trivio.

## Допуслуги в карточке билета

На шаге сопоставления полей доступны:

- `additional_service_types` — «Виды доп. услуг», множественное поле **Строка**.
  Передаётся массив названий (например, «Багаж», «Выбор места»). Кнопка создания
  поля автоматически включает множественность. Поле типа «Список» с ID вариантов
  не подходит для этого сопоставления.
- `additional_service_files` — «Документы дополнительных услуг» (Trivio), отдельное
  множественное поле **Файл**. Включите загрузку документов на шаге запуска.
  Основной билет по-прежнему сопоставляется через `ticket_file` в другое поле.
- `ticket_amount`, `service_fee`, `additional_amount` — цена билета без комиссии,
  комиссия сервиса и стоимость допуслуг с их сборами. `amount` в карточке билета
  содержит стоимость билета с комиссией плюс связанные допуслуги.

Для Trivio итоговая `total_price` распределяется между билетами одной услуги
пропорционально их стоимости с точностью до копейки. Комиссия не добавляется
повторно, если уже включена в итог. При отсутствии итоговой цены используются
переданные тариф, таксы и сборы; по одному неоднозначному `totalcost` комиссия
повторно не прибавляется. Точные суммы для таких ответов требуют сверки с Trivio.

Допуслуга связывается с основным билетом по базовому номеру из описания, номеру
билета или однозначной связи услуги/заказа. При нескольких подходящих билетах
сумма не распределяется произвольно. Прикреплённые файлы берутся из `service_files`
строго по `service_file_service_id`, удалённые вложения пропускаются. Содержимое
получается через штатный метод кабинета `POST /api/file/json`, `getFileContent`
с `source=service` и `fileId`; используется та же сессия Client API. Это работает
и для багажа автобуса / произвольной услуги без `ticketId`. Для EMD без вложений
сохраняется загрузка через `printBlank` с собственными `serviceId` и `ticketId`.
Если Trivio файл не выдаёт, приложение
повторяет попытку в следующем запуске, сохраняя ранее загруженный набор файлов.
Если у допуслуги нет ни прикреплённых файлов, ни собственного `ticketId`, основной
билет вместо документа допуслуги не подставляется. Бинарный файл проверяется по
сигнатуре; допустимы PDF, PNG, JPEG и ZIP размером до 20 МБ.

При полной сверке `getOrder` удалённые допуслуги убираются из управляемых полей.
При неполном ответе очереди сохраняются ранее известные допуслуги. Для проверки
поведения без реальных API и базы выполните `php tests/additional-services.php`.

```powershell
Copy-Item .env.example .env

```

| Параметр | Значение |
|---|---|

| Первоначальная установка | `https://your-domain.example/install.php` |

## Планировщик

Запускайте диспетчер каждую минуту. Внутренний интервал каждой компании
(`30`, `60` или `180` минут) проверяется самим приложением.

Linux cron:

```cron
* * * * * cd /var/www/travel-sync && /usr/bin/php bin/sync.php
15 3 * * * cd /var/www/travel-sync && /usr/bin/php bin/cleanup.php
```

Windows Task Scheduler:

```powershell
php C:\apps\travel-sync\bin\sync.php
php C:\apps\travel-sync\bin\cleanup.php
```

Если расписание синхронизаций создаётся отдельно, очередь можно обработать командой:

```bash
php bin/worker.php --max-jobs=20
```

Worker обновляет heartbeat и прогресс после получения данных и каждые 10 записей.
Задача с отсутствующим heartbeat более 10 минут помечается как аварийно завершённая,
после чего следующий запуск может продолжить синхронизацию.

Для Timeweb задайте минутное расписание для полного пути к `bin/sync.php`; не вызывайте
`public/api.php?action=sync.run` из cron. Проверка доступности приложения находится по
адресу `public/health.php`, а обезличенный технический журнал — в `var/app.log`.

Точечный диагностический запуск:

```bash
php bin/sync.php --member=BITRIX_MEMBER_ID --provider=trivio
```

## Маршрутизация по воронкам

Все услуги создаются в выбранном смарт-процессе. Для каждого типа отдельно
задаются воронка (`categoryId`) и начальная стадия (`stageId`):

- авиабилеты → «Билеты»;
- проживание, отели и хостелы → «Хостелы»;
- ж/д → «Железнодорожные билеты»;
- трансферы и остальные услуги → выбранные администратором направления.

Если тип услуги выключен или для него не выбрана воронка, такая услуга будет
отмечена в статистике как пропущенная и не попадёт в CRM.

## Синхронизация затрат

Пятый шаг мастера включает независимую синхронизацию затрат. Для неё можно выбрать другой
смарт-процесс, воронку, стадию, ответственного и отдельное сопоставление полей. Повторный запрос
к тревел-сервису не выполняется: затраты строятся из того же нормализованного пакета, что и карточки
билетов.

Одна карточка затраты соответствует одному билету либо одному проживанию. Багаж и выбор места присоединяются к билету
последовательно по номеру билета, ID услуги либо по однозначной паре «заказ + пассажир». До возврата сумма
затраты равна стоимости билета и найденных дополнительных услуг. При возврате сохраняются первоначальная
стоимость, возвращённая сумма, штраф, невозвратная часть и итоговая фактическая затрата. Полный возврат
без удержания обнуляет фактическую затрату, частичный возврат оставляет только невозвращённую сумму.
Если провайдер сообщает отмену, но не передаёт размер возврата, последняя известная сумма не обнуляется
наугад, а операция получает отметку «требуется проверка». Если связь неоднозначна,
допуслуга не создаёт самостоятельную затрату и отражается в статистике как пропущенная. Для отеля или
хостела в затрату передаются стоимость, гость, название, адрес, номер комнаты, даты заселения и выселения
и ссылка на заказ.

Для защиты от дублей используется отдельное обязательное поле `expense_external_id`. Его значение
имеет вид `expense:provider:ticket_external_id`, поэтому карточка затраты не конфликтует с карточкой
самого билета даже при выборе одного смарт-процесса.

Существующее сопоставление поля `amount` продолжает работать: теперь это фактическая сумма затраты.
Для подробного учёта на шаге 5 можно дополнительно создать и сопоставить поля `original_amount`,
`refund_amount`, `penalty_amount`, `non_refundable_amount`, `net_amount`, `expense_status_label` и
`calculation_status_label`.

## Local и Marketplace

`APP_DISTRIBUTION=local` используется для разработки на одном портале.
`APP_DISTRIBUTION=marketplace` использует тот же код, но client id/secret
выдаются кабинетом разработчика и являются общими для всех установок.

В режиме `APP_DISTRIBUTION=marketplace` приложение требует MySQL. Версионируемые
миграции применяются автоматически при запуске. Перенос существующей SQLite-базы
описан в [docs/mysql-migration.md](docs/mysql-migration.md), а готовность к публикации —
в [docs/marketplace-readiness.md](docs/marketplace-readiness.md).

## Быстрая работа мастера настройки

Шаги 2–5 не используют cron и не ждут фоновых агентов. Браузер делает один запрос к серверу
приложения, а сервер обращается к Bitrix24 только при отсутствии актуального кэша. Смарт-процессы
кэшируются на 30 минут, поля на 10 минут, воронки и стадии на 15 минут, сотрудники на 60 минут.
Кэш разделён по `member_id`, поэтому данные разных порталов не смешиваются.

Стадии и сотрудники подгружаются после показа основной формы и не блокируют открытие шага.
Если Bitrix24 временно отвечает медленно, сервер отдаёт последнюю успешно сохранённую копию и пишет
результат запроса в `var/app.log` как событие `ui.metadata.completed`. Кнопки «Обновить» на шагах
принудительно запрашивают свежие данные. Таблица `bitrix_metadata_cache` создаётся автоматической
миграцией версии 6 при первом запуске обновлённого приложения. Одновременные запросы одного
справочника объединяются файловой блокировкой, поэтому медленный ответ Bitrix24 не занимает все
PHP-процессы хостинга одинаковой работой.

Журнал синхронизации не входит в первоначальный `bootstrap`: он загружается только при открытии
шага 6. SQL сразу ограничивает результат последними 20 запусками; миграция версии 7 добавляет индекс
по порталу, провайдеру и времени запуска. Это особенно важно при расписании каждые 5 минут.

Сохранённые сопоставления всех подключений и последние полученные справочники Bitrix24 входят в один
`bootstrap`-ответ. Поэтому переходы между шагами 2–5 не создают отдельный запрос только ради чтения
сопоставлений из MySQL. Внешний запрос выполняется лишь тогда, когда нужного справочника ещё нет в
серверном кэше, либо администратор явно нажал кнопку обновления.

## Автоматическая синхронизация и уведомления

Планировщик `bin/sync.php` запускается cron-ом каждую минуту, но ставит новые задачи только после
истечения выбранного в приложении интервала: 5, 10, 15, 30, 60 или 180 минут. Автоматический запуск каждый
раз идемпотентно перепроверяет выбранный период: последний 1, 7 или 30 дней.

Расписание рассчитывается для компании целиком: новый автоматический цикл начинается, когда подошёл
срок всех подключённых провайдеров, после чего Aviasales, Smartway и Trivio ставятся в одну очередь.
Это удерживает их на общей 15-минутной сетке и формирует одно сводное уведомление вместо нескольких.

После автоматического цикла выбранные сотрудники получают одну сводку через
`im.notify.system.add`: получено от API, создано, обновлено и ошибок. Ручные проверочные запуски
уведомлений не отправляют.

Сводка сначала сохраняется в таблице `notification_outbox`. Если Bitrix24 временно не принимает
уведомление, cron повторяет отправку с увеличивающимся интервалом до одного часа. Уведомление
захватывается одним процессом на 10 минут, поэтому параллельные запуски cron не дублируют доставку.
Повтор использует тот же уникальный `TAG`, поэтому Bitrix24 заменяет предыдущую сводку этого цикла,
если первый ответ был потерян после фактической доставки.
При появлении нового автоматического отчёта предыдущий ещё не отправленный отчёт того же портала
помечается устаревшим. Поэтому восстановление права `im` не приводит к отправке пачки старых сводок.

Для этой функции у локального приложения должны быть права CRM, уведомления (`im`) и основные
данные пользователей (`user_basic`) и управление пользовательскими полями (`userfieldconfig`). В `.env` укажите
`BITRIX24_SCOPE=crm,im,user_basic,userfieldconfig`, добавьте
эти права в настройках локального приложения Bitrix24 и повторно откройте приложение внутри портала
от имени администратора. Проверенный placement-токен сохраняется при каждом открытии.

Приложение проверяет фактическую доступность `crm.item.add`, `crm.item.update` и
`im.notify.system.add` через `method.get`, а не считает строку scope из `.env` доказательством
выданных прав. В журнал аудита записывается только короткий SHA-256-отпечаток токена, источник,
срок действия и результат проверки методов; сами OAuth-токены в журнал не попадают.

Перед серверным обращением к Bitrix24 приложение проверяет срок действия OAuth-токена. После истечения
`access_token` оно без участия браузера обменивает сохранённый `refresh_token`, сразу сохраняет новую
пару токенов и повторяет временные ошибки OAuth. Из ответа обновления адрес портала берётся только из
`client_endpoint`: поле `domain` в этом ответе обозначает OAuth-сервер и не может заменить домен портала.
Открывать приложение ночью для
обычного продления токена не требуется. Повторная установка нужна только если Bitrix24 уже отозвал
сам `refresh_token` (например, после удаления или переустановки приложения без сохранения нового
контекста).

Создание карточки не повторяется автоматически после неопределённого сетевого таймаута, чтобы не
создать дубль при потерянном ответе. Ответ `METHOD_NOT_FOUND` обрабатывается отдельно: приложение
проверяет доступность метода и повторяет `crm.item.add` только когда Bitrix24 подтверждает, что метод
существует и разрешён текущему токену.
